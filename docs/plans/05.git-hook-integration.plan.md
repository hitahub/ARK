# Opt-in Git hook integration

## Status

Proposed for discussion. This plan scopes an optional integration between
`arc health` and Git commits; it does not authorize implementation or silent
hook installation.

## Objective

Let users run ARC's existing report-only vault checks before committing, while
keeping Git integration explicit, reversible, and safe for repositories that
already have hooks.

## Current behavior

`arc health [path]` reports broken local Markdown and wikilinks, likely orphan
notes, and structural verification findings. It does not modify the vault.
ARC currently has no Git hook integration. Git hooks are local to a clone by
default, and repositories may already use their own hook manager or scripts.

## Proposed scope

- Support an explicit user action to configure or remove ARC's Git integration.
- Run the existing health checks through Git's pre-commit lifecycle; do not
  duplicate or subtly change health-check rules.
- Never install, enable, overwrite, or remove a hook as a side effect of
  `arc init`, `arc health`, or another existing command.
- Preserve unrelated existing Git hook configuration and clearly report
  conflicts rather than replacing user-owned hooks.
- Provide a dry-run or preview before changing hook configuration.
- Keep health checks read-only; do not fix links, move notes, or alter staged
  files automatically.
- Document that hooks are local configuration and are not an access-control,
  security, or CI guarantee.

## Safety and compatibility requirements

- Resolve and validate the selected vault and Git repository explicitly;
  handle non-Git directories and linked hook paths safely.
- Do not overwrite an existing hook or hook-manager configuration. Any
  supported coexistence strategy must preserve the existing hook's behavior.
- Make installation and removal idempotent and narrowly scoped to ARC-owned
  files or clearly marked ARC-managed content.
- Surface filesystem, Git, and health-check errors; do not silently skip a
  configured hook.
- Keep the hook fast enough for an interactive commit, or document and provide
  a clear opt-out for users whose vaults make checks too slow.
- Avoid network access and external services.

## Decisions for discussion

1. **Integration mechanism:** direct `core.hooksPath` configuration,
   hook-manager integration, or a standalone ARC-managed hook wrapper.
2. **Installation interface:** a dedicated `arc hook install|uninstall`
   command, or another explicit command contract.
3. **Scope:** whether to support only pre-commit, and how to select the vault
   when the Git root and vault root differ.
4. **Existing hooks:** whether to reject occupied hook locations or support
   safe chaining with documented limitations.
5. **Failure policy:** whether any health finding blocks a commit, whether
   users can select finding types, and how commits can proceed when a check
   fails.
6. **Distribution:** whether this is a local developer convenience only, or
   also needs a documented CI example.

## Out of scope

- Automatically enabling hooks during initialization or updates.
- Rewriting notes, repairing links, changing staged content, or enforcing
  repository-wide policy.
- Replacing a team's existing hook manager or treating local hooks as a
  substitute for CI.
- Adding checks beyond the current `arc health` behavior in the initial
  integration.

## Acceptance criteria

- Users can preview, explicitly install, and remove ARC's integration without
  losing pre-existing hook behavior or unrelated Git configuration.
- Commits with no configured ARC hook behave exactly as before.
- A configured hook invokes the documented health checks for the intended
  vault and reports findings and operational errors clearly.
- Tests cover install/remove idempotency, dry-run, existing hook conflicts,
  failure behavior, non-Git paths, and path safety.
- CLI help and relevant guides explain setup, local scope, limitations, and
  opt-out/removal.

## Validation plan

- Unit and CLI tests for the acceptance criteria above.
- Integration tests using temporary Git repositories and temporary vaults.
- Run the repository's existing formatting, test, typecheck, and build
  commands after implementation.
- Manually verify that an existing unrelated hook is preserved and that
  commits remain unaffected until explicit installation.
