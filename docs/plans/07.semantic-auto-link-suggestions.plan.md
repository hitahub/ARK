# Semantic auto-link suggestions

## Status

The initial offline lexical workflow is implemented as
`arc links suggest <vault-path>`. It analyzes direct Markdown notes in
`300_Slipbox/`, prints a bounded report, and never writes to the vault.
Explicit local report saving and opt-in local Ollama embedding matching are
also implemented. Lexical matching remains the default; caching remains
exploratory. See the [saved report plan](09.saving-link-suggestion-reports.plan.md),
[semantic matching evaluation](10.evaluating-semantic-link-matching.plan.md),
and [semantic matching discussion](https://github.com/hitahub/arc/discussions/28)
for details.

## Objective

Help users discover related notes in the Slipbox by surfacing explainable,
reviewable link suggestions. The feature must not edit notes or create links
automatically.

## Problem and proposed direction

As a Slipbox grows, useful relationships between notes can be difficult to
find through tags or exact text search alone. An opt-in local workflow could
identify potentially related notes and present candidates for the user to
review and apply themselves.

The initial implementation is the explicit command
`arc links suggest <vault-path>`. It uses a dependency-free lexical matcher,
requires an explicit vault path, and prints its report to stdout. The matching
is a heuristic for manual review, not a claim that two notes are related.

## Initial implementation decisions

- **Note scope:** Direct, non-hidden Markdown files in `300_Slipbox/` only.
- **Matching approach:** Deterministic TF-IDF cosine similarity with a small
  built-in stop-word list; front-matter and code blocks are excluded.
- **Results:** Print at most 20 candidate pairs to stdout, including similarity
  and up to five shared terms. A candidate needs at least two shared terms and
  a score of at least 0.12.
- **Limits:** At most 500 notes, 64 KiB per note, 8 MiB total content, 100,000
  unique terms, 2,000 directory entries, and 1,000,000 term-pair comparisons.
  Fail explicitly instead of returning a partial report when a limit is
  exceeded.
- **Default matcher:** Dependency-free lexical matching. Semantic matching is
  separately selected with `--semantic --model <name>`.
- **Model and cache:** No bundled model or cache. The user must install Ollama
  and a compatible embedding model separately. Semantic mode only sends note
  text to the fixed local endpoint `127.0.0.1:11434`; it never contacts a
  remote service.
- **Report writes:** Source notes are never modified. The existing `--output`
  option saves a new report outside the vault; it never replaces a file.

Caching still requires a separate scope decision and must preserve the
privacy and read-only requirements below.

## Optional local semantic matching

`arc links suggest <vault-path> --semantic --model <name>` explicitly selects
an installed Ollama embedding model. This mode sends cleaned note text to the
fixed loopback embedding endpoint only, ranks all note pairs by cosine
similarity, and prints up to 20 candidates. It has additional limits of 100
notes, 8,000 characters per note, and 512,000 semantic input characters.
Unlike the lexical matcher, it applies no minimum score threshold, so lower
ranked suggestions may be unrelated and require careful review. See the
[evaluation plan](10.evaluating-semantic-link-matching.plan.md) for the
synthetic comparison and limitations.

## Safety and privacy requirements

- Never modify, annotate, rename, or create links in source notes.
- Never send note contents, embeddings, or metadata to a remote service.
- Semantic matching is opt-in and may send note text only to the fixed local
  Ollama endpoint at `127.0.0.1:11434`. No endpoint override, remote service,
  or automatic model download is supported. Model acquisition is a separate,
  explicit user action.
- Keep analysis opt-in and scoped to the explicitly selected vault; do not
  silently choose a vault or scan outside the approved content scope.
- Reject or safely handle symlinks, traversal, and paths outside the vault,
  following established repository path-safety patterns.
- Bound note sizes, scan work, and suggestion counts; surface unsupported
  input and operational failures clearly rather than silently skipping them.
- Treat suggestions as heuristics. Clearly communicate that users must review
  each candidate and that no links are automatically applied.

## Out of scope for the initial implementation

- Automatically adding or rewriting wikilinks, front-matter, or note content.
- Hosted inference, third-party APIs, account setup, or background sync.
- Automatic model downloads, vault-wide indexing on existing commands, or
  hidden/always-on processing.
- Generated summaries, answers, or claims that a suggested relationship is
  authoritative.
- Changing the existing `arc health`, `arc verify`, or MCP server behavior.

## Acceptance criteria for the initial implementation

- The command requires an explicit vault path and only reads the approved
  direct Slipbox note scope.
- The implementation remains explicit and offline; no source note is modified
  and no remote service receives vault data.
- Candidate limits, error behavior, and the user review workflow are
  documented and tested.
- The dependency-free method is bounded, deterministic, and exposes shared
  terms so users can review why candidates were ranked.
- Tests cover note/path boundaries, empty and large vaults, limits,
  determinism, errors, and proof that source notes remain unchanged.

## Validation expectations

The implementation PR should run the repository checks:

Add focused tests for the selected algorithm and exact output contract,
input/path validation, limits, failure reporting, and the absence of source
