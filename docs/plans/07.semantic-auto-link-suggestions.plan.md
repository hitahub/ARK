# Semantic auto-link suggestions

## Status

Proposed idea; implementation scope and technical choices are not yet agreed.
The [roadmap](../roadmap.md#4-semantic-auto-link-suggestions) describes the
direction as an offline workflow, potentially using a local model. This plan
defines the questions and guardrails to resolve before implementation. Track
the proposal in [issue #27](https://github.com/hitahub/ARK/issues/27) and
discuss it in [discussion #28](https://github.com/hitahub/ARK/discussions/28).

## Objective

Help users discover related notes in the Slipbox by surfacing explainable,
reviewable link suggestions. The feature must not edit notes or create links
automatically.

## Problem and proposed direction

As a Slipbox grows, useful relationships between notes can be difficult to
find through tags or exact text search alone. An opt-in local workflow could
identify potentially related notes and present candidates for the user to
review and apply themselves.

The initial proposal is an explicit command that analyzes eligible notes and
prints or saves a bounded report of candidate links. It should work offline
after any explicitly configured local model is available. The command name,
report format, eligible note scope, and matching approach remain open for
discussion before implementation.

## Proposed planning decisions

Resolve these choices with maintainers and contributors before implementation:

- **Note scope:** Decide which Markdown notes are eligible. Prefer a narrow,
  documented content scope and exclude hidden paths, templates, archive
  content, and generated files unless explicitly approved.
- **Matching approach:** Compare a local embedding model with simpler lexical
  approaches and existing metadata/tag-based discovery. Select a method based
  on quality, install size, runtime, supported platforms, and maintenance
  burden; do not assume an embedding dependency is justified.
- **Model lifecycle:** If embeddings are selected, decide how users choose and
  obtain a model, whether model files are optional dependencies, and how
  version changes or missing models are reported. Do not download models or
  make network requests implicitly.
- **Suggestion quality:** Define similarity scoring, duplicate/self-match
  handling, result limits, and any minimum threshold. Prefer stable,
  understandable output and avoid claiming that a score proves a relationship.
- **User workflow:** Decide whether results are printed, written to a
  user-selected report path, or both. Any report write must be explicit,
  bounded, and must not overwrite an existing file without confirmation.
- **Incremental work:** Determine whether caching is necessary. If proposed,
  define its location, invalidation/versioning, privacy implications, and
  behavior when stale or corrupt. No cache should be created during unrelated
  commands.

## Safety and privacy requirements

- Never modify, annotate, rename, or create links in source notes.
- Never send note contents, embeddings, or metadata to a remote service.
- Do not make network requests or download models as a side effect of running
  ARC. Any future model acquisition must be a separate, explicit user action
  with documented provenance and licensing.
- Keep analysis opt-in and scoped to the explicitly selected vault; do not
  silently choose a vault or scan outside the approved content scope.
- Reject or safely handle symlinks, traversal, and paths outside the vault,
  following established repository path-safety patterns.
- Bound note sizes, scan work, and suggestion counts; surface unsupported
  input and operational failures clearly rather than silently skipping them.
- Treat suggestions as heuristics. Clearly communicate that users must review
  each candidate and that no links are automatically applied.

## Out of scope for the initial implementation

- Automatically adding or rewriting wikilinks, frontmatter, or note content.
- Hosted inference, third-party APIs, account setup, or background sync.
- Automatic model downloads, vault-wide indexing on existing commands, or
  hidden/always-on processing.
- Generated summaries, answers, or claims that a suggested relationship is
  authoritative.
- Changing the existing `arc health`, `arc verify`, or MCP server behavior.

## Pull request scope

Implementation should remain opt-in, independently reviewable, and must follow
the decisions recorded here. Split work only where each change can be reviewed
and tested independently; update this plan before implementation diverges from
the agreed scope.

| Change                           | Scope                                                                                                                    | Example Conventional Commit subject          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| Suggestion discovery             | Add the explicit command and bounded, read-only candidate discovery using the agreed matching method.                    | `feat(links): suggest related Slipbox notes` |
| Local model support, if approved | Add only the explicitly selected local model integration and its documented setup; no implicit downloads or network use. | `feat(links): add optional local embeddings` |
| Documentation and workflow       | Document eligibility, setup, privacy, limitations, output, and manual review workflow.                                   | `docs(links): document link suggestions`     |

## Acceptance criteria for implementation planning

- Maintainers agree on eligible note scope, matching method, model lifecycle
  (if applicable), output/report behavior, and whether caching is needed.
- The implementation remains explicit and offline; no source note is modified
  and no remote service receives vault data.
- Candidate limits, error behavior, and the user review workflow are specified.
- The chosen approach has a feasible dependency, platform, performance, and
  maintenance story.
- Tests are planned for note/path boundaries, empty and large vaults, limits,
  deterministic behavior where applicable, errors, and proof that source notes
  remain unchanged.

## Validation expectations

The implementation PR should run the repository checks:

```bash
pnpm format:check
pnpm test
pnpm typecheck
pnpm build
```

Add focused tests for the selected algorithm and exact output contract,
input/path validation, limits, failure reporting, and the absence of source
note writes. Record the exact commands and results in the implementation PR.
