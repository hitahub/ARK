# ARC Obsidian Plugin Companion Plan

## Objective

Provide an optional Obsidian companion for ARC vaults without coupling
Obsidian-specific APIs to the ARC CLI. Keep filesystem checks read-only, make
note creation explicit, and defer AI-client synchronization.

## Implementation decisions

- Keep CLI and plugin sources in `src/cli/` and `src/obsidian-plugin/`, with a
  single root `package.json`.
- Treat Slipbox subfolders as reportable warnings; do not claim to enforce a
  rule against external filesystem changes.
- Create notes only through an explicit command, use native ARC-compatible
  starter content, and never overwrite an existing note.
- Report unresolved wikilinks in the active note; do not rewrite links or
  attempt subjective "unclear link" judgments.
- Defer AI-client task-context sync and community-directory submission. Build
  community-ready files locally for a later release.

## Execution phases

### Phase 1: Unified package and plugin build

- [x] Add an Obsidian plugin manifest and an independent bundle build.
- [x] Keep plugin dependencies and scripts in the single root package.
- [x] Add plugin build and typecheck coverage to root CI validation.
- [x] Keep plugin build output at `dist/obsidian-plugin/`, separate from CLI output.

### Phase 2: Read-only Slipbox warnings

- [x] Check direct child folders inside `300_Slipbox/`.
- [x] Refresh findings after vault changes and show them in a status-bar report.
- [x] Keep the check advisory; never move or delete notes.

### Phase 3: Explicit ARC note creation

- [x] Add a command to create concept, project, and task notes.
- [x] Use metadata compatible with ARC templates and dashboard queries.
- [x] Preserve existing notes by selecting an available filename.

### Phase 4: Wikilink diagnostics

- [x] Report unresolved wikilinks in the active note using Obsidian's link
      resolution cache.
- [x] Show target and line number without modifying note content.
- [x] Add unit tests for embeds, aliases, headings, and resolved targets.

### Phase 5: Documentation and validation

- [x] Document local build, installation, behavior, and limitations.
- [x] Correct the CLI command list in the roadmap.
- [x] Run tests, type checking, and both CLI and plugin builds.
- [ ] Smoke-test status-bar interactions and note creation in Obsidian.

## Acceptance criteria

The plugin builds independently, creates notes only after user action, never
overwrites or relocates existing notes, and reports only the supported
structural and link findings. AI-client synchronization remains outside the
initial implementation.
