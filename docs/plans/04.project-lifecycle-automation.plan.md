# Project lifecycle automation plan

## Objective

Define and scope the next implementation-ready capability for ARC: a safe project lifecycle command that archives completed work while preserving the vault's metadata model, dashboard behavior, and user trust.

## Current status

The roadmap already distinguishes implemented features from future work. The CLI, plugin install flow, and link-diagnostics improvements are implemented and documented. The project lifecycle automation idea remains explicitly deferred and therefore makes a strong candidate for a formal repo plan: the command is already named in the roadmap, the safety requirements are clear, and the feature maps cleanly onto the existing ARC structure.

## Recommended feature

The planning target is a command with the following shape:

```bash
arc archive <Project-Name>
```

This command should move a completed project out of `200_Projects/` into archive storage, update the project metadata to reflect archived state, and avoid destructive or surprising file-system changes.

## Proposed scope

### 1. Command contract and UX

- Confirm the command name and syntax.
- Define interactive and non-interactive confirmation behavior.
- Clarify whether the command supports a dry run or preview mode.
- Define how project names map to folder locations in `200_Projects/`.

### 2. Safety rules

The plan must define explicit behavior for:

- archive-target collisions,
- partial move failures,
- rollback or recovery if the move fails mid-flight,
- symlinked folders or special file entries,
- preserving their vault links and note metadata.

### 3. Metadata and dashboard integration

The command must remain consistent with ARC's documented metadata conventions.

- Project status should be updated to a stable archival state.
- Archived projects should no longer appear as active project work.
- Dashboard queries and templates should continue to work as documented.

### 4. Testing strategy

The implementation should include tests for:

- successful archive moves,
- confirmation decline paths,
- collision handling,
- backup or rollback behavior,
- invalid project names and missing directories,
- dashboard and metadata consistency checks.

## Implementation phases

### Phase 1: Requirements and UX

- Confirm the command contract and proposed archive destination.
- Define the required confirmation and dry-run flows.
- Decide which project metadata fields are updated during archiving.

### Phase 2: Filesystem safety logic

- Implement safe move behavior with collision handling.
- Add rollback or best-effort recovery when errors occur.
- Preserve vault links and note content without destructive edits.

### Phase 3: Metadata and dashboard updates

- Update project status to archived or equivalent state.
- Ensure active Dashboard queries no longer include archived work.
- Validate compatibility with the existing project templates and docs.

### Phase 4: Documentation and validation

- Add repo documentation for the archive flow and safety rules.
- Update planning docs and the roadmap summary where needed.
- Validate the command against test and build requirements.

## Success criteria

This feature is ready for implementation when all of the following are true:

- the command contract is explicit,
- the archive safety model is documented,
- rollback and collision rules are defined,
- metadata and dashboard impacts are confirmed,
- and tests cover the main failure and cancellation scenarios.

## Notes

This idea remains in the roadmap as a future capability specifically because it needs requirements and safety review before implementation. That makes it an ideal next planning target: it is valuable, has a stable home in the CLI, and does not broaden the project into more speculative AI or publishing architecture before the core vault lifecycle is addressed.
