# ARC-aware MCP server

## Status

Implemented on `feat/arc-aware-mcp-server`; scope was agreed in
[issue #25](https://github.com/hitahub/arc/issues/25).

## Objective

Provide an optional Model Context Protocol (MCP) interface for ARC vault data
so compatible AI clients can retrieve structured, ARC-aware context without
relying only on generic filesystem tools. The server must make its access
boundaries explicit and must not imply that structured responses prevent
hallucinations or enforce vault security.

## Agreed initial scope

- Implement a separately invoked local MCP server using the standard input and
  output transport, with diagnostics sent to standard error.
- Launch through `arc mcp <vault-path>`. Require an explicit vault root, resolve
  and validate it before serving requests, and do not silently select another
  vault.
- Use the current official TypeScript MCP SDK and its supported protocol
  version. Pin a compatible SDK dependency in the package manifest.
- Use an established YAML parser with explicit schema validation for supported
  front-matter fields.
- Start with read-only tools:
  - `get_active_projects()` returns project index notes under
    `200_Projects/` whose YAML front-matter has `type: project` and
    `status: active`.
  - `search_slipbox_by_tag(tag)` searches direct Markdown files in
    `300_Slipbox/` for the requested front-matter tag.
  - `get_note(path)` returns an individual project index or direct Slipbox note
    only when its path is inside the selected vault and permitted content
    scope.
- Only expose project index notes and direct Slipbox notes. Reject hidden paths,
  symlinks, traversal, and content outside those areas. Do not use
  `.claudeignore` as an access-control mechanism.
- Return stable, documented structured output and actionable protocol errors
  for invalid arguments, inaccessible paths, unsupported content, and I/O
  failures.
- Define and test limits for search inputs, result counts, and note content so
  a request cannot accidentally return an entire large vault.
- Document that the server runs with the invoking user's filesystem
  permissions. It is not a sandbox, access-control system, or security
  boundary against a client that already has broader filesystem access.

The initial release is read-only. Changes to tool names, response shapes, or
write capabilities require an agreed scope update before implementation.

## Decisions

- The first release supports the current official TypeScript MCP SDK and its
  supported protocol version. Client-specific configuration examples will be
  documented without automatically changing client configuration.
- The initial tool set is limited to the three listed read-only tools. Any
  additional tools require a separately agreed scope.
- Content is allowlisted to project index notes and direct Markdown files in
  `300_Slipbox/`. Hidden paths, symlinks, and every other vault location are
  excluded. `.claudeignore` is advisory and is not interpreted by the server.
- Front-matter is parsed as YAML with explicit validation of the fields each
  operation consumes; malformed YAML or invalid consumed fields produce
  actionable tool errors.
- The server is launched with `arc mcp <vault-path>`, and the vault path is
  mandatory.
- Write-capable operations remain out of scope and require a separate plan.

## Data contract and limits

- The MCP SDK negotiates the protocol version with the client. The package uses
  `@modelcontextprotocol/sdk` `^1.32.2`.
- `get_active_projects()` returns `{ projects: [{ path, title, status }],
truncated }`; `status` is `active`.
- `search_slipbox_by_tag(tag)` returns `{ tag, notes: [{ path, title, tags }],
truncated }`; tag matching is case-insensitive after trimming.
- `get_note(path)` returns `{ path, content, sizeBytes }`.
- Paths are vault-relative. Project indexes must be below
  `200_Projects/<project>/`; Slipbox notes must be direct Markdown children of
  `300_Slipbox/`.
- The request tag limit is 128 characters; path limit is 1,024 characters.
  Returned titles are limited to 256 characters; a note may have at most 100
  tags, each at most 128 characters.
- Note content is limited to 65,536 bytes. Each scan is limited to 2,000
  directory entries and 8 MiB of note data. Each search returns at most 50
  results and sets `truncated: true` when more matches exist. The stdio
  transport rejects messages larger than 256 KiB.
- Scan-budget overflows are errors, not partial results. A 50-result cap is
  the only condition represented as a truncated result.

## Safety and compatibility requirements

- Never write to the vault in the initial read-only release.
- Canonicalize requested paths and reject traversal, symlinks, or other
  resolution paths that escape the selected vault. Apply the same boundary to
  index-derived paths.
- Do not execute shell commands, fetch network resources, or follow external
  links while serving requests.
- Avoid returning excluded or out-of-scope content. Document that exclusions
  are application behavior, not a security boundary when the client has direct
  filesystem access.
- Do not silently skip malformed metadata or file errors; return useful errors
  without exposing unrelated host paths or contents.
- Define limits for search inputs, result counts, and content size, and test
  their exact behavior.
- Keep server startup opt-in. Do not start a server, register clients, change
  client configuration, or transmit vault data as a side effect of `arc init`.
- Use only protocol-supported output and error mechanisms; do not mix
  diagnostics into standard output.

## Out of scope

- Creating or editing notes, tasks, or project metadata.
- Automatically configuring AI clients or syncing context to remote services.
- Embeddings, semantic search, ranking, or generated answers.
- Treating MCP tool availability or structured output as authorization or
  protection against prompt injection.
- A hosted or multi-user server.

## Acceptance criteria

- Users can explicitly start the server against a selected vault and receive
  protocol responses without contaminating standard output with diagnostics.
- Only the approved read-only tools are exposed in the initial release.
- Tool schemas and response structures are documented and stable for the
  supported client versions.
- Invalid inputs, oversized requests/results, malformed metadata, filesystem
  errors, and protocol errors are handled explicitly and tested.
- Tests prove that requested and index-derived paths cannot escape the vault,
  including through traversal and symlinks.
- Documentation explains client setup, data scope, filesystem permissions,
  limits, privacy implications, and the lack of security isolation.
- Existing CLI commands and vault contents are unchanged unless the user
  explicitly starts the new server.
