# Evaluating semantic link matching

## Status

Limited evaluation completed for the implemented, offline lexical
`arc links suggest <vault-path>` workflow and one local embedding model. On a
small synthetic set, the embedding ranking recovered more judged relevant
pairs at ranks 5 and 10 than the lexical ranking. This is a promising signal,
not enough evidence to approve semantic matching for implementation. Current
CLI behavior remains unchanged.

See the exploratory [semantic auto-link suggestions plan](07.semantic-auto-link-suggestions.plan.md)
and [discussion #28](https://github.com/hitahub/arc/discussions/28).

## Objective

Determine whether an optional, local semantic matcher improves discovery of
related Slipbox notes enough to justify its dependency, model lifecycle,
performance, and maintenance costs. Preserve the existing lexical command as
the default and as a baseline.

Suggestions remain candidates for manual review. ARC must never create or
modify links or note content automatically.

## Evaluation proposal

Compare the current lexical matcher with a bounded set of candidates:

- The existing TF-IDF lexical matcher, unchanged as the baseline.
- A lexical or metadata-ranking refinement that adds no model runtime.
- An optional embedding matcher that runs locally using a model obtained and
  configured explicitly by the user.

Use a small, manually curated evaluation set with relevance judgments.
Evaluate candidate quality at the top results, explainability, runtime,
resource use, dependency and distribution size, supported platforms, and
operational complexity. Do not include personal vault content, note text, or
embeddings in the repository or send them to a service. Document the
methodology and results so maintainers can decide whether to proceed.

No production model, quality threshold, scoring method, or command-line
interface is approved by this proposal. `nomic-embed-text` was evaluated as a
single candidate only; implementation decisions require review of these
results and further evaluation.

## Evaluation results

This is a small, synthetic feasibility check, not evidence of performance on
real vaults. The notes and judgments below were created for this evaluation;
no personal vault content was used or committed.

### Method

- Constructed 12 short synthetic notes and manually judged six note pairs as
  relevant for this set. All other pairs were treated as not relevant for this
  evaluation, not as universally unrelated.
- Ran the current `arc links suggest` implementation with unchanged defaults.
  For a like-for-like ranking comparison, also ranked all 66 unordered pairs
  using the same TF-IDF scores with the production thresholds disabled. The
  command itself continues to return only pairs meeting its existing
  shared-term and similarity thresholds.
- Compared one no-model refinement: lower the minimum shared-term requirement
  from two terms to one while retaining the existing 0.12 cosine floor and
  ranking. It was evaluated over the same notes and judgments.
- Embedded the same complete note text locally with `nomic-embed-text:latest`
  using Ollama 0.40.11 and cosine-ranked all 66 unordered pairs. The model was
  downloaded separately after explicit approval; the evaluation sent note
  text only to the local Ollama endpoint.
- For the all-pairs rankings, precision at _k_ is relevant pairs among the
  first _k_ of 66, and recall at _k_ is those hits divided by the six judged
  relevant pairs. The production-command result counts are reported
  separately, because it filters and can return fewer than _k_ candidates.

### Quality

| All-pairs ranking                  | Hits @5 | Precision @5 |   Recall @5 | Hits @10 | Precision @10 |  Recall @10 |
| ---------------------------------- | ------: | -----------: | ----------: | -------: | ------------: | ----------: |
| TF-IDF scores, thresholds disabled |     4/5 |          80% | 4/6 (66.7%) |     5/10 |           50% | 5/6 (83.3%) |
| `nomic-embed-text:latest` cosine   |     5/5 |         100% | 5/6 (83.3%) |     6/10 |           60% |  6/6 (100%) |

The production lexical command returned four candidates, all judged relevant;
its output therefore had 4/4 hits (100% precision among returned candidates)
and 4/6 recall (66.7%). The one-term refinement also returned the same four
candidates. In the all-pairs comparison, both methods had 100% precision
through rank 3. Embeddings ranked the graph/network paraphrase third and the
queue/calendar pair eighth; the lexical command filtered out both. The
embedding ranking also placed two non-relevant calendar/sleep pairs at ranks
6 and 7, so its full ranking is not uniformly better.

The baseline ranked password managers / credential vaults (29.7%), composting
/ soil microbiome (28.9%), circadian rhythm / sleep timing (23.3%), and spaced
repetition / retrieval practice (19.6%). All four were judged relevant in this
set. Lowering the shared-term requirement did not add candidates; the existing
cosine floor remained in effect.

The result set is intentionally small and hand-curated; its perfect precision
at the top of this ranking is not a general quality estimate. There is no
statistical significance claim or target threshold. The judgments, single
model, single short-note set, and single machine do not establish expected
production quality.

### Operational comparison and limitations

| Dimension                 | Existing TF-IDF baseline                                            | One-term refinement                         | Local embeddings                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Quality on this set       | 4/6 from the production command; 4/5 at rank 5 in all-pairs ranking | Same as baseline                            | 5/6 at rank 5 and 6/6 at rank 10                                                                                                   |
| Explanation               | Shared terms and deterministic score are shown                      | Same explanation; no added value observed   | Cosine score only; no term-level explanation                                                                                       |
| Runtime                   | One CLI run: 144 ms wall time                                       | Same scoring approach; not separately timed | 12-note batch: first successful request 820 ms wall time including 527 ms model load; later warm batch 106 ms                      |
| Resource and distribution | No model runtime or model artifact                                  | No model runtime or model artifact          | Model artifact 274 MB; peak memory and CPU use not measured                                                                        |
| Platform and lifecycle    | Existing supported CLI platforms                                    | Same as baseline                            | `nomic-embed-text` Apache-2.0 model via Ollama 0.40.11; tested on one Mac only; setup, upgrades, and other platforms not evaluated |

Timing values are single observations on this machine, not a performance
benchmark. The warm batch latency is comparable to the single lexical CLI
measurement in scale, but embedding model load and runtime footprint remain
additional costs. No separate ARC dependency was added. Source note contents
were verified unchanged, and all embedding requests used the local Ollama
endpoint; no note text or vectors were sent to a remote service.

### Recommendation

Keep the current lexical matcher unchanged and do not yet implement semantic
matching. This one model improved measured recall at ranks 5 and 10 on this
synthetic set, including one paraphrase missed by the lexical command, which
supports a larger follow-up evaluation. The gain is not enough to justify
shipping a runtime or selecting this model for users. Before implementation,
maintainers should validate on a larger, independently judged synthetic or
explicitly licensed set, compare more than one suitable local embedding model,
and measure repeated latency, peak resource use, explanation quality, and
platform and model-lifecycle costs. This is a deferral for insufficient
evidence, not a finding that semantic matching cannot help.

## Proposed implementation boundaries

If maintainers approve implementation after evaluation:

- Keep lexical matching as the default; semantic matching must be explicitly
  selected by the user.
- Require a local model that the user has obtained and configured separately.
  Do not download models, make network requests, or contact hosted inference
  services from ARC.
- Do not add a cache in the first implementation. Reconsider caching only
  with a documented invalidation and privacy design.
- Keep the explicitly selected vault and existing direct-note scope, unless a
  separate scope review approves a change.
- Preserve bounded input and work limits, clear errors, deterministic output
  where feasible, and a concise explanation that suggestions are heuristic.
- Keep source notes read-only. Reuse the current report behavior, including
  optional `--output`, rather than introducing a separate persistence model.
- Document any scoring explanation needed for users to review why candidates
  appear. Similarity scores must not be presented as proof of a relationship.

The interface for selecting a matcher and configuring a local model remains a
decision for the implementation proposal; this document does not prescribe
flag names, configuration files, a model format, or a specific library.

## Safety and privacy requirements

- Never modify, annotate, rename, or create links in source notes.
- Never send note contents, metadata, or embeddings to a remote service.
- Do not make network requests or download models as a side effect of ARC
  commands. Model acquisition must be a separate, explicit user action with
  documented provenance and licensing.
- Keep matching opt-in and scoped to the explicitly selected vault.
- Bound input sizes, scan work, resource consumption, and suggestion counts;
  surface unsupported input and operational failures clearly.
- Apply existing path-safety protections to model and vault paths; do not
  follow unsafe symlinks or allow traversal outside the intended scope.
- Do not treat organizational folders or ignore conventions as access-control
  boundaries.
- Do not make semantic matching a dependency of `arc health`, `arc verify`,
  initialization, or the MCP server.

## Out of scope

- Hosted inference, third-party APIs, account setup, or background sync.
- Automatic model downloads or bundling a model with the CLI.
- Automatic note edits, wikilink creation, or generated claims that a match is
  authoritative.
- Making semantic matching the default or changing existing lexical results.
- Persistent caches, embeddings indexes, background indexing, or vault-wide
  indexing on existing commands.
- Changes to the current report format or saved-report safety contract.

## Decision gates

Before implementation is approved, maintainers should review:

1. Whether the evaluation demonstrates a meaningful improvement over the
   lexical baseline for the intended discovery use case.
2. Whether that improvement justifies the runtime and model setup burden across
   supported platforms.
3. Whether users can provide and configure a compatible model without ARC
   downloading it or transmitting vault data.
4. The matcher selection interface, scoring explanation, resource limits, and
   failure behavior.
5. Whether the first implementation should proceed, be narrowed to a
   non-model refinement, or be deferred.

## Acceptance criteria for the evaluation

- The evaluation methodology and manually curated judgments are documented;
  no private vault content is committed.
- The current lexical matcher, no-model refinement, and a local embedding
  candidate are measured on the same bounded evaluation set.
- Quality, explainability, runtime/resource use, dependency footprint,
  platform support, and model lifecycle are compared, with unmeasured
  dimensions explicitly identified.
- No production behavior, dependency, model artifact, cache, or network path
  is added to ARC. The evaluation model was acquired separately with explicit
  user approval, and note embeddings were generated locally.
- The result and a recommendation are recorded for maintainer review. An
  embedding implementation remains gated on a separate model evaluation.

## Validation expectations

The evaluation should use synthetic or explicitly licensed sample notes and
run locally. Do not use personal vaults as shared or committed test data.
Any later implementation proposal should include focused tests for matcher
selection, determinism, limits, failure handling, and proof that source notes
remain unchanged, in addition to the repository checks:

```bash
pnpm format:check
pnpm test
pnpm typecheck
pnpm build
```
