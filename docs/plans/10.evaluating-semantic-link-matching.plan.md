# Evaluating semantic link matching

## Status

Limited synthetic evaluation completed for the implemented, offline lexical
`arc links suggest <vault-path>` workflow and one local embedding model.
Results showed higher embedding recall at ranks 10 and 20 on the expanded
synthetic set. This small, manually judged evaluation is not evidence of
general quality; implementation is proceeding as an explicitly approved,
opt-in follow-up. The lexical command remains the default.

See the exploratory [semantic auto-link suggestions plan](07.semantic-auto-link-suggestions.plan.md)
and [discussion #28](https://github.com/hitahub/arc/discussions/28).

## Objective

Determine whether an optional, local semantic matcher improves discovery of
related Slipbox notes enough to justify its dependency, model lifecycle,
performance, and maintenance costs. Preserve the existing lexical command as
the default and as a baseline.

Suggestions remain candidates for manual review. ARC must never create or
modify links or note content automatically.

## Evaluation method

Compare the current lexical matcher with a bounded set of candidates:

- The existing TF-IDF lexical matcher, unchanged as the baseline.
- A lexical or metadata-ranking refinement that adds no model runtime.
- An optional embedding matcher that runs locally using a model obtained and
  configured explicitly by the user.

Use a small, manually curated evaluation set with relevance judgments.
Evaluate candidate quality at the top results, explainability, runtime,
resource use, dependency and distribution size, supported platforms, and
operational complexity. Do not include personal vault content in the
repository or send any vault data to a remote service. Document the
methodology and results so maintainers can decide whether to proceed.

`nomic-embed-text` was evaluated as one candidate. Based on these results and
the user's approval, the initial optional interface uses explicit
`--semantic --model <name>` selection and the model's cosine similarity.
No score threshold is inferred from this small evaluation.

## Evaluation results

This is a synthetic feasibility check, not evidence of performance on real
vaults. The notes and judgments below were created for this evaluation; no
personal vault content was used or committed. A first 12-note run was followed
by an expanded 24-note set. Both used the same six then twelve manually judged
related pairs.

### Method

- Constructed a 12-note set and then extended it with 12 more short synthetic
  notes. Judged one related pair per topic, for six judgments in the initial
  set and twelve in the expanded set. All other pairs were treated as not
  relevant for this evaluation, not as universally unrelated.
- Ran the current `arc links suggest` implementation with unchanged defaults.
  For a like-for-like ranking comparison, also ranked all unordered pairs
  using the same TF-IDF scores with the production thresholds disabled. The
  command itself continues to return only pairs meeting its existing
  shared-term and similarity thresholds.
- Compared one no-model refinement: lower the minimum shared-term requirement
  from two terms to one while retaining the existing 0.12 cosine floor and
  ranking. It was evaluated over the same notes and judgments.
- Embedded the same complete note text locally with `nomic-embed-text:latest`
  using Ollama 0.40.11 and cosine-ranked all 66 unordered pairs in the first
  set and all 276 pairs in the expanded set. The model was downloaded
  separately after explicit approval; the evaluation sent note text only to
  the local Ollama endpoint.
- For the all-pairs rankings, precision at _k_ is relevant pairs among the
  first _k_ of the available pairs, and recall at _k_ is those hits divided by
  the judged relevant pairs for that set. The production-command result counts
  are reported separately, because it filters and can return fewer than _k_
  candidates.

6 and 7, so its full ranking is not uniformly better.

### Operational comparison and limitations

| Dimension                 | Existing TF-IDF baseline                                               | One-term refinement                         | Local embeddings                                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Quality on expanded set   | 4/12 from the production command; 5/12 at rank 10 in all-pairs ranking | Same as baseline                            | 7/12 at rank 10 and 10/12 at rank 20                                                                                               |
| Explanation               | Shared terms and deterministic score are shown                         | Same explanation; no added value observed   | Cosine score only; no term-level explanation                                                                                       |
| Runtime                   | One 24-note CLI run: 213 ms wall time                                  | Same scoring approach; not separately timed | 24-note batch: 485 ms Ollama server time including 265 ms model load                                                               |
| Resource and distribution | No model runtime or model artifact                                     | No model runtime or model artifact          | Model artifact 274 MB; peak memory and CPU use not measured                                                                        |
| Platform and lifecycle    | Existing supported CLI platforms                                       | Same as baseline                            | `nomic-embed-text` Apache-2.0 model via Ollama 0.40.11; tested on one Mac only; setup, upgrades, and other platforms not evaluated |

Timing values are single observations on this machine, not a performance
benchmark. Embedding model load and runtime footprint remain additional costs.
No separate ARC dependency was added. Source note contents were verified
unchanged, and all embedding requests used the local Ollama endpoint; no note
text or vectors were sent to a remote service.

### Recommendation

The expanded set shows a promising recall/precision tradeoff for this one
model: top-10 recall rose from 41.7% to 58.3%, and top-20 recall rose from 50%
to 83.3%, while top-20 precision rose from 30% to 50%. The gains are
synthetic, manually judged, and based on one model and one machine; they do not
establish general quality or settle runtime and lifecycle costs. Following
the user's explicit approval, proceed with an opt-in implementation while
preserving lexical matching as the default. Keep the implementation narrow
and revisit model choice and quality with real-world, user-controlled
evaluation before making it the default or bundling any model.

## Proposed implementation boundaries

Approved initial implementation boundaries:

- Keep lexical matching as the default; semantic matching must be explicitly
  selected by `--semantic --model <name>`.
- Require an already-installed local Ollama model selected explicitly by the
  user. In semantic mode only, ARC sends note text to the fixed loopback
  endpoint `http://127.0.0.1:11434/api/embed`; it accepts no configurable
  endpoint and never contacts a remote or hosted service or downloads a model.
- Do not add a cache in the first implementation. Reconsider caching only
  with a documented invalidation and privacy design.
- Keep the explicitly selected vault and existing direct-note scope, unless a
  separate scope review approves a change.
- Preserve bounded input and work limits (100 notes, 8,000 characters per
  semantic note, 512,000 semantic characters total), clear errors,
  deterministic output where feasible, and a concise explanation that
  suggestions are heuristic.
- Keep source notes read-only. Reuse the current report behavior, including
  optional `--output`, rather than introducing a separate persistence model.
- Document any scoring explanation needed for users to review why candidates
  appear. Similarity scores must not be presented as proof of a relationship.

The user must install/configure Ollama separately and explicitly provide its
model name. The matcher and model selection flags are not available to health,
verify, initialization, or MCP commands.

## Safety and privacy requirements

- Never modify, annotate, rename, or create links in source notes.
- Never send note contents, metadata, or embeddings to a remote service.
- Only the explicit semantic mode may send content to the fixed local Ollama
  loopback endpoint. Never accept a configurable endpoint, make remote
  requests, or download models. Model acquisition must be a separate explicit
  user action with documented provenance and licensing.
- Keep matching opt-in and scoped to the explicitly selected vault.
- Bound input sizes, scan work, resource consumption, and suggestion counts;
  surface unsupported input and operational failures clearly.
- Apply existing path-safety protections to model and vault paths; do not
  follow unsafe symlinks or allow traversal outside the intended scope.
- Do not treat organizational folders or ignore conventions as access-control
  boundaries.
- Do not make semantic matching a dependency of `arc health`, `arc verify`,
  initialization, or the MCP server.

## Out of scope

- Hosted inference, third-party APIs, account setup, or background sync.
- Automatic model downloads or bundling a model with the CLI.
- Automatic note edits, wikilink creation, or generated claims that a match is
  authoritative.
- Making semantic matching the default or changing existing lexical results.
- Persistent caches, embeddings indexes, background indexing, or vault-wide
  indexing on existing commands.
- Changes to the current report structure or saved-report safety contract;
  semantic mode reuses that structure with a matcher-specific score explanation.

## Follow-up review

As the feature is exercised, maintainers should review:

1. Whether broader user-controlled evaluation confirms an improvement over
   the lexical baseline for the intended discovery use case.
2. Whether that improvement justifies the runtime and model setup burden
   across supported platforms.
3. Whether users can provide and configure a compatible model without ARC
   downloading it or transmitting vault data remotely.
4. Whether the selected interface, score explanation, resource limits, and
   failure behavior remain usable as the feature is exercised.
5. Whether semantic matching should remain optional, be narrowed, or be
   deferred after real-world feedback.

## Acceptance criteria for the evaluation

- The evaluation methodology and manually curated judgments are documented;
  no private vault content is committed.
- The current lexical matcher, no-model refinement, and a local embedding
  candidate are measured on the same bounded evaluation sets.
- Quality, explainability, runtime/resource use, dependency footprint,
  platform support, and model lifecycle are compared, with unmeasured
  dimensions explicitly identified.
- The implementation keeps the lexical matcher as default and requires
  explicit semantic mode and model selection.
- No production model artifact, cache, remote network path, or automatic model
  download is added to ARC.
- The result and recommendation are recorded for maintainer review. The
  implementation remains opt-in and does not claim semantic similarity is
  proof of a relationship.

## Validation expectations

The evaluation uses synthetic notes and runs locally. Do not use personal
vaults as shared or committed test data. The implementation includes focused
tests for matcher selection, determinism, limits, failure handling, and proof
that source notes remain unchanged, in addition to the repository checks:

```bash
pnpm format:check
pnpm test
pnpm typecheck
pnpm build
```
