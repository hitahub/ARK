# Publishing selected content

## Status

Implemented as the local-only `arc publish` workflow. Remote publication,
synchronization, and content-level secret detection remain out of scope.

## Objective

Export a controlled subset of ARC Markdown to a new local review directory
without exposing known private metadata, copying excluded folders, or changing
the source vault.

## Problem statement

The CLI accepts explicit file/directory selections, an output location, and
repeatable vault-relative exclusions. It previews the resolved selection,
strips all YAML front-matter, and requires confirmation before creating output
unless `--yes` is supplied. Export is local-only.

## Proposed user-facing scope

- Export only explicitly selected Markdown files and directories.
- Require a new output directory outside the source vault.
- Exclude hidden content, ARC templates/settings/archives, and explicitly
  excluded paths.
- Remove all front-matter and reject known private or ambiguous privacy markers.
- Preview a deterministic file list and confirm before writing.
- Keep export local and reviewable; no remote publication is performed.

## Requirements and safety constraints

- Default to read-only behavior; publishing must not modify the source vault.
- Respect excluded folders and any known private or sensitive metadata fields.
- Require a transparent preview step before a publishable artifact is produced.
- Fail closed when the selection is ambiguous, incomplete, or unsafe.
- Keep exported output separate from the live vault and avoid incidental
  filesystem writes outside the target output directory.
- Support local-only review before any remote publishing step is introduced.
- Make the security and privacy boundaries explicit in user documentation.

## Implemented behavior

- `arc publish <vault-path> <selection...> --output <directory>`
- Repeatable `--exclude <vault-relative-path>`, `--dry-run`, and `--yes`.
- Bounded scans, deterministic Markdown path preservation, symlink rejection,
  and rollback of incomplete writes.
- See [Getting started](../getting-started.md#publish-behavior) for the full
  user-facing policy and limitations.

## Out of scope for the initial proposal

- Automatic synchronization to AI clients or external systems.
- Unreviewed remote publication without explicit user confirmation.
- Rewriting notes, moving files, or altering source metadata during export.
- Embedding or server-side processing beyond a clearly defined output format.
- Open-ended tagging or semantic publishing heuristics before the scope is
  defined and reviewed.

## Suggested design principles

- Explicit selection beats inference.
- Local preview beats silent export.
- Privacy-by-default applies to metadata and excluded folders.
- Deterministic output is easier to reason about and easier to review.
- Publish only what the user has intentionally chosen.

## PR and commit ruleset

The repository requires Conventional Commits for both commit subjects and pull
request titles. The validation regex is:

```regex
^(build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test){1}(\([\w\-\.]+\))?(!)?: ([\w ])+([\s\S]*)
```

Examples of valid messages:

- `feat: add publish preview workflow`
- `fix: filter private metadata from export`
- `docs: document publish exclusion rules`

Examples of invalid messages:

- `publish selected content`
- `feature: add export preview`
- `Update docs for publishing`

## Acceptance criteria

- Users can select a bounded content set for publication.
- The system respects excluded folders and privacy-sensitive metadata.
- A preview or dry run is available before any publish step is executed.
- Export output is generated without modifying the vault source state.
- The feature is clearly documented as an explicit user action, not implicit
  behavior.
- Test coverage verifies selection, exclusions, preview behavior, and safety
  failures.
